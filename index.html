Bringing Word documents into a docs-as-code repo

Moving to docs-as-code usually starts with a folder full of .docx files: runbooks, onboarding guides, policies. Pasting them into a Markdown editor gives you one undifferentiated wall of text, because copy-paste throws away the one thing Word did know, which lines were styled Heading 1 or Heading 2. Here is a repeatable way to bring Word documents into a Git repo with their structure intact.

Why style-based conversion matters

Word documents carry structure in their style names. A line styled "Heading 2" is genuinely a second-level heading. Converters that read the styles, rather than the visual formatting, give you real ## headings, real lists and real tables. The dochost Word to Markdown converter does this in the browser: it maps style names onto Markdown structure and keeps tables, links and bold text, and the .docx is never uploaded.

The workflow

  1. Fix the source first. In Word, make sure the headings use Heading styles, not just bigger bold text. Five minutes here saves an hour later.
  2. Convert one document and save it as docs/<area>/<slug>.md.
  3. Extract the images into docs/<area>/img/ and fix the paths.
  4. Clean the Word artefacts: empty bold markers, non-breaking spaces, "smart" quotes inside code, manual numbering such as "1.1.2" typed into headings.
  5. Open a pull request per document, so the owner can review the Markdown diff.

Things Word does that Markdown can't

  • Merged table cells: split them, or turn the table into a list of sections.
  • Comments and tracked changes: resolve them before converting. They won't come across.
  • Text boxes and floating shapes: rewrite them as a blockquote or a note.
  • Headers and footers: drop them. Your docs site has its own.

Converting web-based docs too

Some of the old documentation will live on an intranet page rather than in a .docx. For those, HTML to Markdown gives you the same kind of output from the page source, so both sources end up in one consistent format.

Review checklist for each PR

  • Heading levels are in order (one # per file)
  • Tables render on GitHub
  • Internal links point to the new .md paths
  • No images still pointing at a local C:\ path
  • The owner is listed in front matter
